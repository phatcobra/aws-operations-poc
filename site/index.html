      What this page can—and cannot—prove

      The public update is a sanitized copy of a bounded window of CloudWatch logs. It is not continuous monitoring, an uptime measurement, or a direct view of the CloudWatch alarm. Updates publish after a successful deployment or an owner-started refresh. Old or unavailable updates are explicitly marked unknown.

      The deployment evidence separately verifies the attempt sequence in DynamoDB and matching log events. A recorded weather response alone does not prove a database write succeeded. No temperature value is displayed because the public data contract does not include it.

      01 How does it run without me?+

      EventBridge starts a Python 3.12 Lambda once per hour. The function asks Open-Meteo for New York City’s current temperature, then attempts to save each outcome to DynamoDB and emits a structured CloudWatch log.

      Compute
      128 MB Lambda · 20-second timeout
      Storage
      DynamoDB on-demand · one record per attempt
      Logs
      14-day retention
      Infrastructure definition ↗
      02 What keeps retries under control?+

      A single loop allows at most three attempts. The worker waits 0.5 seconds before attempt two and 1 second before attempt three. A normal response ends the loop immediately. Three failed attempts end this run; the hourly schedule remains enabled.

      EventBridge target retries are configured to zero. This setting does not itself control Lambda’s separate asynchronous invocation behavior. Handled request failures return a recorded outcome instead of throwing a function error.

      The simulation follows the deterministic verifier’s scenarios. In those failure tests, an exception is deliberately raised before making the weather request; it is not a real outage of the weather provider.

      Worker and retry policy ↗
      03 How is a deployment proven?+

      GitHub Actions runs offline tests and validates CloudFormation. OIDC supplies short-lived deployment credentials. After deployment, the verifier invokes all three scenarios, queries DynamoDB with a consistent read, and checks for matching CloudWatch events.

      Expected results: success on attempt 1; recovery on attempt 2; and exhaustion after exactly 3 failed attempts. A failed assertion fails the deployment workflow. The public summary is read from the resulting evidence artifact—not guessed from an animation.

      Live verification assertions ↗
      04 What does monitoring actually detect?+

      CloudWatch holds structured logs, native Lambda metrics, an operator dashboard, and an invocation heartbeat alarm. The alarm watches for missing invocations in two consecutive hourly periods. It has no notification or repair actions attached.

      That native metric includes manual and deployment-test invocations; it does not isolate scheduled runs. This page’s hourly-check signal instead uses log records labeled scheduled. Handled request failures are visible in those records and may not appear as Lambda Errors.

      Alarm and dashboard configuration ↗
      05 What can a public visitor control?+

      Only this browser’s simulation, filters, and explanation controls. There is no public AWS API, function trigger, deployment trigger, database write, or credential in this site.

      GitHub Actions reads this POC’s existing log group and publishes allowlisted fields as a static JSON file. The browser reads that same-origin file. No new AWS infrastructure or always-on server is needed. The existing publisher role retains its deployment permissions, but no role or credential is exposed to the browser.
